The Kokkos User Group (KUG) meeting at HPSF 2026 took place in Chicago, IL, from March 16th to March 20th. The program brought together Kokkos developers, library maintainers, and application teams to share updates on performance portability work across the Kokkos ecosystem, with recurring discussion topics including GPU performance tuning, interoperability (especially with Fortran), memory management, and distributed execution. The full schedule (including talk pages, and slides/recordings where available) can be accessed via the HPSF schedule links referenced throughout this report.

# Day 1 (Thursday):

Thursday focused primarily on Kokkos usage in applications and libraries, along with adoption experiences and training-related discussions.

A number of talks highlighted end-to-end application workflows and the combination of Kokkos with other ecosystem components. In multi-GPU radiative transport work integrated into OpenFOAM, the presenter described improvements for both performance and scalability by grouping rays and using ArborX for spatial searches; speedups of approximately 400× over serial and 10× over OpenMP were reported (https://hpsf2026.sched.com/event/2EfW5/multi-gpu-radiative-transport-in-participating-media-with-kokkos-nicolas-tricard-massachusetts-institute-of-technology). In high-order CFD, batching was presented as a key technique to improve GPU performance, and the importance of evaluating the performance of the complete solver (not only individual kernels) was emphasized (https://hpsf2026.sched.com/event/2ESjP/optimizing-compact-difference-schemes-for-high-order-cfd-with-kokkos-sana-nazir-purdue-university). For particle methods, updates on CabanaPD reported that a multimaterial extension is now usable and that performance on MI250 GPUs remained reasonable even with conditional logic in the main kernel path (https://hpsf2026.sched.com/event/2ESjS/exploring-kokkos-performance-for-many-species-particle-systems-with-cabanapd-sam-reeve-oak-ridge-national-lab).

Several presentations centered on ecosystem libraries and portability challenges encountered in practice. A talk on a portable mesh interpolation library described using ArborX for neighbor searches while implementing interpolation separately, and outlined a migration away from Eigen toward Kokkos-Kernels due to incomplete GPU support in Eigen; the project is planned to be open-sourced (https://hpsf2026.sched.com/event/2ESjV/a-portable-data-interpolation-library-using-kokkos-and-arborx-ramzi-messahel-safran). Memory management was also a topic: an experimental implementation of Umpire as a Kokkos memory space was presented as ongoing work in a separate repository (https://hpsf2026.sched.com/event/2ESk2/umpirespace-the-kokkos-memory-space-youve-always-wanted-kristi-belcher-lawrence-livermore-national-lab).

Adoption-oriented talks addressed programming model choices and developer experience. A presentation on performance-portable SIMD for vector PIC noted that natural vectorization can be effective but may not match hand-optimized performance, and discussed the use of AoSoA to maintain a clean interface while enabling good performance (https://hpsf2026.sched.com/event/2ESk8/lessons-learned-porting-vector-particle-in-cell-to-performance-portable-simd-nigel-tan-los-alamos-national-laboratory). Framework integration perspectives were provided by talks on MOOSE and deal.II: MOOSE’s use of dynamic polymorphism and constraints around separate compilation and RDC were discussed as challenges for accelerator use (https://hpsf2026.sched.com/event/2ESjY/kokkos-moose-planning-the-future-of-moose-on-accelerators-namjae-choi-idaho-national-laboratory), while deal.II reported bundling Kokkos and highlighted the role of Kokkos training in enabling student contributions (https://hpsf2026.sched.com/event/2EfYq/kokkos-in-the-dealii-finite-element-library-timo-heister-clemson-university). On the Python front, a pyKokkos update described kernel fusion efforts and a shift away from exposing Kokkos::View directly in favor of NumPy interoperability and explicit copies, motivated in part by compilation-time concerns (https://hpsf2026.sched.com/event/2ESkB/pythonizing-pykokkos-ivan-grigorik-the-university-of-texas-at-austin).

Training and education sessions concluded the day with discussion of effective instructional practices and documentation usability. Notes emphasized the value of hands-on components, the usefulness of recorded materials, and the observation that C++ fundamentals are often a larger barrier than Kokkos concepts. Documentation search behavior was also identified as an area for improvement (e.g., common terms not consistently surfacing the most relevant pages) (https://hpsf2026.sched.com/event/2ESjh/teaching-domain-scientists-enough-c++-for-accelerators-using-their-python-or-r-proficiency-pariksheet-nanda-university-of-pittsburgh, https://hpsf2026.sched.com/event/2EfcJ/how-hard-is-it-to-transition-a-team-of-fortran-developers-to-kokkos-daniel-holladay-los-alamos-national-laboratory, https://hpsf2026.sched.com/event/2Efd9/discussion-on-teachingtraining-daniel-holladay-los-alamos-national-laboratory-pariksheet-nanda-university-of-pittsburgh-hariprasad-kanna-cea-john-holmen-oak-ridge-national-laboratory).

# Day 2 (Friday):
Friday broadened to topics related to performance mechanisms, distributed execution, build/packaging, and Fortran interoperability and migration paths.

Performance-focused talks included updates on library capabilities and execution policies. Kokkos-FFT reported that MPI support is a key next step and that communication costs were a dominant factor in some performance testing (https://hpsf2026.sched.com/event/2ESjq/kokkos-fft-updates-yuuichi-asahi-cea). A talk on MDRangePolicy efficiency discussed differences between serial loop behavior (including limited autovectorization) and `parallel_for` execution, and outlined possible directions for improved SIMD utilization while noting the difficulty of vectorizing arbitrary user functors (https://hpsf2026.sched.com/event/2ESjt/towards-more-efficient-mdrangepolicy-execution-hariprasad-kannan-cea). For spectral element kernels, hardware-aware tiling and chunking were presented as effective for accelerating 3D stencil computations; comparisons noted that CuTe achieved higher performance in part through overlapping loads and computation, motivating interest in more explicit data-movement overlap strategies (https://hpsf2026.sched.com/event/2ESkN/hardware-aware-tiling-for-performance-portable-spectral-element-kernels-rohit-kakodkar-princeton-university). Application package updates included mixed precision support in the Kokkos package for LAMMPS (https://hpsf2026.sched.com/event/2EfeU/improvements-to-the-kokkos-package-in-lammps-trung-nguyen-university-of-chicago).

Build and packaging concerns were addressed in the Build & Packaging working group session, including approaches to simplifying downstream consumption of Kokkos, handling cases where downstream projects should not inherit wrappers such as `nvcc_wrapper`, updates on Spack packaging, Kokkos-on-Godbolt, and ongoing efforts toward binary distribution (https://hpsf2026.sched.com/event/2ESjw/build-and-packaging-wg-how-do-i-get-the-kokkos-i-want-with-minimal-effort-jakob-bludau-oak-ridge-national-lab).

Several talks addressed extending Kokkos to new environments and scaling models. A neuromorphic integration update described ongoing work toward a Kokkos backend targeting neuromorphic/heterogeneous systems, with incremental implementation progress and early support for `deep_copy` and work toward `parallel_for` (https://hpsf2026.sched.com/event/2ESjz/neuromorphic-integration-into-the-kokkos-ecosystem-bradley-theilman-sandia-national-laboratories). For distributed multi-GPU execution, KokkosComm was presented as a communication layer designed to manage lifetimes and abstract non-contiguous data handling, with NCCL and RCCL backends (https://hpsf2026.sched.com/event/2I3ti/kokkoscomm-communication-layer-for-distributed-kokkos-applications-nicolas-morales-sandia-national-laboratories).

A substantial portion of Friday covered Fortran interoperability and modernization strategies. A Kokkos Fortran interop update recommended using the `develop` branch given the age of available pre-release versions and noted current limitations such as lack of automatic memory management and primarily SharedSpace support (https://hpsf2026.sched.com/event/2EfhX/kokkos-fortran-interop-bruno-turcksin-oak-ridge-national-lab). In parallel, an approach for automatic translation of Fortran to Kokkos described using flang-derived AST information to generate C++ boilerplate and highlighted the need to correctly detect reductions (https://hpsf2026.sched.com/event/2EfXj/automatic-translation-of-fortran-to-kokkos-brayden-wagoner-los-alamos-national-laboratory). Application integration reports included introducing a C++/Kokkos dynamical core behind an existing Fortran interface in an earth system model (https://hpsf2026.sched.com/event/2ESjM/utilizing-a-kokkos-based-dynamical-core-in-a-fortran-based-earth-system-model-jian-sun-nsf-national-center-for-atmospheric-research) and porting portions of a Fortran plasma simulation library to C++/Kokkos with C bindings back into Fortran, with memory access to the previous timestep identified as a primary performance concern (https://hpsf2026.sched.com/event/2EfaL/porting-a-fortran-plasma-simulation-to-exascale-on-amd-gpus-using-both-openmp-and-kokkos-yuuichi-asahi-cea).

Additional sessions addressed specialized performance and scaling issues. An in-kernel inference talk (PONNI) reported that `bfloat16` DRAM loads/stores were close in cost to float in their measurements (https://hpsf2026.sched.com/event/2ESkE/portable-low-latency-in-kernel-inferencing-of-small-neural-networks-with-kokkos-matthew-norman-oak-ridge-national-lab). ExaCA performance optimization work described imbalance challenges and preprocessing efforts, with remaining scaling limitations noted (https://hpsf2026.sched.com/event/2Efg2/scalability-and-performance-optimization-for-exaca-matt-rolchigo-oak-ridge-national-lab). A proposal for RangePolicy-compatible per-iteration scratch memory discussed desired functionality and potential contributions (https://hpsf2026.sched.com/event/2ESk5/a-rangepolicy-compatible-per-iteration-scratch-memory-implementation-daniel-holladay-los-alamos-national-laboratory).
